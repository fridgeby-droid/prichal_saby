# Причал 0.6.1 — Bothost + Timeweb Cloud

В архиве полный проект. Dockerfile в корне. Запускается один процесс Python, один экземпляр приложения.

## Что входит

- Литры: выбор в интерфейсе от 1 л с шагом 0,5 л; в корзине внутреннее количество в мл, в Saby и ЮKassa передаётся количество в литрах. Цена прайса — за 1 л. Проверка остатка отдельно по точке. Вес остаётся от 150 г с шагом 50 г.
- Общий прайс 66 для 12 магазинов. РЦ в шаблон не включён.
- Одна общая пара ключей ЮKassa для всех точек; shopId фиксируется до первого запроса платежа. Нет переключения платежа на кассу другого магазина при изменении настроек.
- PostgreSQL поддерживает TLS и CA Timeweb. Каталог, заказы, сообщения, соответствие заказов темам хранятся в базе.
- Фото: локально либо S3. S3 работает с приватным бакетом; ссылки выдаются на час. Публичный бакет также поддерживается.
- Закрытая группа -1004496259606. Первое сообщение по заказу создаёт тему. Любой участник может ответить покупателю через «Ответить» на пересланный ботом вопрос в этой теме. Обычные сообщения остаются внутри группы. Покупатель видит «Магазин», ID и имя сотрудника сохраняются в support_audit.
- Если сотрудник закрыл тему штатной кнопкой Telegram, бот повторно открывает её при следующем вопросе. Анонимные сообщения администраторов и сообщения других ботов не пересылаются: сотруднику нужно писать от своего аккаунта.
- Замены подписей из возвращённого Excel. Пустые ячейки не менялись, надписи «Удалить» удалены. Сценарий и Saby delivery.isPickup=true сохранены; подпись «Доставка» сама по себе не включает курьерскую доставку.
- Автоматическая оплата после оформления сохраняется. Отдельная кнопка «Перейти к оплате» удалена по таблице. При выборе неоплаченного заказа в «Мои заказы» открывается оплата этого же заказа; новый платёж не создаётся при уже сохранённом payment_id.

## Что создать в Timeweb

1. PostgreSQL: для Самовывоза отдельная база prichal_pickup и отдельный пользователь с правами на эту базу/схему. Для Core и AI — отдельные базы и пользователи. Эти проекты данной сборкой не обновляются. Выберите кластер с возможностью дополнительных баз.
2. Включите подключение извне для Bothost, получите доменное имя, порт, логин, пароль и CA-сертификат. По возможности ограничьте доступ исходящим IP Bothost; localhost и приватный IP Timeweb из Bothost не подойдут.
3. S3: отдельный приватный бакет для фото Самовывоза. Для Core и AI — свои бакеты и отдельные ключи. Для ключа приложения нужны чтение, запись и удаление объектов в его бакете. Последнее используется проверкой storage-check для удаления собственного тестового файла.
4. Endpoint/регион берите из панели бакета. В документации Timeweb приведены https://s3.twcstorage.ru и ru-1; при отличающихся значениях используйте панель.

### PostgreSQL

DATABASE_URL имеет вид:

```text
postgresql://USER:PASSWORD@HOST:PORT/prichal_pickup
```

Специальные символы пароля в URL должны быть percent-encoded. Значения host/port/user/db берите из Timeweb. Для доменного TLS-подключения установите DATABASE_SSLMODE=verify-full и DATABASE_SSL_CA_B64 — CA-сертификат из панели, закодированный Base64 одной строкой. Приложение восстановит файл сертификата само. Не подставляйте пароль в DATABASE_SSL_CA_B64.

Чтобы получить Base64, загрузите CA-файл в доступную папку контейнера и выполните отдельной командой:

```text
python manage.py encode-ca /app/data/timeweb-root.crt
```

Вывод вставьте в DATABASE_SSL_CA_B64. Сертификат не является секретным ключом. Альтернативно sslmode и sslrootcert можно передать прямо в DATABASE_URL с абсолютным путём к заранее установленному сертификату; переменные DATABASE_SSLMODE и DATABASE_SSL_CA_B64 тогда оставить пустыми.

| Переменная | Что указать |
|---|---|
| PHOTO_STORAGE | s3 для Timeweb, local до подключения |
| S3_ENDPOINT_URL | HTTPS endpoint из панели |
| S3_REGION | Регион бакета |
| S3_BUCKET | Точное имя бакета |

| S3_SECRET_ACCESS_KEY | Secret Key |
| S3_PREFIX | pickup/photos |
| S3_PUBLIC_BASE_URL | Пусто для приватного бакета. Для публичного — URL корня бакета, без pickup/photos |

При включении S3 текущие локальные фото будут использованы для первичной загрузки, если сохранились. Остальные загрузятся из Saby при синхронизации. Ошибки загрузки фото не стирают прежнюю запись. Автоматического удаления объектов S3 нет: ничего чужого в бакете приложение не очищает. Позже можно настроить отдельную политику хранения.

### Общая ЮKassa для всех магазинов

```text
YOOKASSA_SHOP_ID=ваш_общий_shopId
YOOKASSA_SECRET_KEY=ваш_общий_секретный_ключ
```

Новые платежи всех точек используют только эту пару. Переменные с суффиксами ID магазинов не нужны для новых платежей. Выбранная точка Saby и её остатки сохраняются в заказе независимо от общей ЮKassa.

Если в версии 0.6.0 уже создавались платежи через отдельные кассы, сохраните их ключи до завершения сверки. Для таких заказов используется сохранённый payment_shop_id. Изменение общей пары не переключает уже начатый платёж на другую кассу. При смене общего shopId старый можно сохранить как YOOKASSA_ARCHIVE_SHOP_ID_<старыйShopId> и YOOKASSA_ARCHIVE_SECRET_KEY_<старыйShopId>. Секреты в базе не хранятся.

В общем кабинете ЮKassa задайте URL уведомлений:

```text
https://ВАШ-БОТ.bothost.tech/webhooks/yookassa
```

События payment.succeeded и payment.canceled. Сервер всегда перепроверяет платёж через API кассы, сохранённой в заказе. Сумма, валюта, order_id и account_id проверяются.

Для теста: ALLOW_REAL_PAYMENTS=false, LIVE_ACCEPTANCE_CONFIRMED=false и ключи test_. Для реальных оплат оба флага true после приёмки. Настройки RECEIPT_ENABLED, RECEIPT_VAT_CODE и RECEIPT_TAX_SYSTEM сохраняйте из действующей конфигурации; false в шаблоне — тестовое значение, не решение о фискализации. Полученный ранее тестовый платёж не подтверждает настройку чеков реальной кассы.

## Обновление без переноса базы — можно сделать сейчас

1. Сохраните текущие переменные и резервную копию базы. Загрузите проект 0.6.1 в Bothost, сохранив действующие DATABASE_URL и данные /app/data.
2. Добавьте SUPPORT_GROUP_ID и общую пару ЮKassa. До готовности S3 оставьте PHOTO_STORAGE=local. Не копируйте пустые секреты поверх действующих.
3. Перезапустите приложение. Новые таблицы создаются автоматически, прежние заказы не удаляются.
4. Выполните команды по одной:

```text
python manage.py storage-check
```
```text
python manage.py payments-check
```
```text
python manage.py support-check
```
```text
python manage.py telegram-setup
```
```text
python manage.py catalog-status
```

payments-check проверяет наличие конфигурации, не делает списаний и не проверяет ключ у провайдера. support-check ожидает topics_enabled=true, manage_topics=true. telegram-setup заново устанавливает webhook и кнопку меню, не публикует сообщения продавцам.

Каталог обновляется фоново раз в 5 минут. catalog-sync нельзя запускать одновременно с рабочим процессом синхронизации; при обычном запуске достаточно дождаться catalog-status с актуальным временем.

## Перенос существующих данных на Timeweb

История заказов уже есть: не переключайте DATABASE_URL на пустую базу без резервной копии, если хотите её сохранить. Сам каталог можно восстановить из Saby, историю переписки — только из старой базы.

1. На версии 0.6.1 установите MAINTENANCE_MODE=true и перезапустите Bothost. Приложение ответит 503 на пользовательские запросы и webhook; /health останется доступным. Фоновые задачи остановлены.
2. Экспортируйте в постоянный каталог /app/data (если Bothost его не сохраняет между перезапусками, скачайте файл до изменения окружения):

```text
python manage.py db-export /app/data/pickup-transfer.json
```

3. Скачайте дополнительную копию этого файла. Он содержит контакты и историю покупателей, не кладите его в репозиторий или общую группу. Экспорт не перезаписывает уже существующий файл.
4. Замените DATABASE_URL на Timeweb и заполните TLS-параметры. MAINTENANCE_MODE оставьте true. Перезапустите. Схема пустой базы создастся автоматически.
5. Восстановите копию в новую пустую базу:

```text
python manage.py db-import /app/data/pickup-transfer.json
```

Команда проверяет пустоту всех таблиц приложения; существующие данные не затираются. Все таблицы импортируются одной транзакцией. Сопоставьте количества записей из вывода export/import. Старая база не изменяется.
6. Заполните S3, установите PHOTO_STORAGE=s3. Выполните storage-check: он проверит доступ к базе и запись/чтение/удаление собственного тестового объекта S3.
7. Установите MAINTENANCE_MODE=false, перезапустите. Дождитесь синхронизации каталога и фото; проверьте /health и catalog-status. Старые ожидающие платежи перепроверятся автоматически.
8. Если до открытия приложения импорт/проверка не прошли, верните прежний DATABASE_URL и его TLS-настройки. После появления новых заказов на новой базе простой откат URL уже приведёт к разным историям — сначала нужна сверка данных.

При обновлении только приложения автоматический перенос между разными DATABASE_URL не выполняется.

## Чат и восстановление неопределённого создания темы

Бот должен быть администратором группы с управлением темами. Для отправки покупателю отвечайте именно на сообщение с вопросом, опубликованное ботом; произвольная переписка сотрудников не уходит клиенту. Удалять тему с активным обращением не следует.

Если Telegram создал тему, но ответ API потерялся, повторно создавать её автоматически небезопасно. support-check покажет unresolved_topics. Найдите тему в группе и свяжите её с заказом командой support-attach <полный UUID заказа> <ID темы>; если точно не создана — support-reset <UUID> --confirmed-absent. Эти две команды выполняются при MAINTENANCE_MODE=true, после перезапуска, затем обычный режим возвращается. Они сбрасывают попытки ожидающих сообщений этого заказа.

Сообщения отправляются из очереди, повторяются до 8 попыток. support-check показывает pending_messages. При неопределённом результате отправки Telegram сообщение может прийти повторно; у sendMessage нет ключа идемпотентности. Входящие обновления Telegram дедуплицируются по update_id. Для уведомлений в личном Telegram покупателю нужно предварительно запустить бота; переписка в MiniApp сохраняется независимо от доставки личного уведомления.

## Проверка перед приёмом заказов

- В каждом магазине проверьте литровый товар: 1 л → 1,5 л, сумму и индивидуальный остаток.
- Проверьте тестовый платёж выбранной точки в общем кабинете ЮKassa и заказ в Saby.
- Из заказа отправьте вопрос: создаётся одна тема; ответ сотрудника виден покупателю. Повторный вопрос и перезапуск приложения не создают новую тему.
- С закрытой темой отправьте новый вопрос: тема снова открывается.
- Фото должны оставаться доступны после перезапуска Bothost и обновления каталога.

Локальные автоматические тесты не заменяют проверку с вашими ключами Timeweb, Saby, Telegram и ЮKassa. Никакие реальные платежи при подготовке архива не выполнялись.
