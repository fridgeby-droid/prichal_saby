# Обновление 0.4.2 — диагностика передачи заказа Saby

Сохраняется причина ошибки order/create: HTTP-статус, доступное сообщение API
или ошибка формата ответа. Секреты и известные контакты заказа маскируются.
Успешный externalId сохраняется до уведомлений: сбой уведомления не меняет
принятый заказ на неопределённый. Неопределённые заказы не повторяются автоматически.

После обновления можно прочитать состояние заказа:

```sh
python manage.py order-diagnostics ID_ЗАКАЗА
```

Команда не отправляет заказ, не вызывает оплату и не печатает контакты покупателя.
Для ошибок из старых версий причину восстановить нельзя: она не сохранялась.
Сначала проверьте наличие заказа в Saby по точке, сумме и номеру в примечании.
Если заказ есть — нужно привязать его настоящий externalId; если отсутствует —
сначала выяснить настройки точки, затем согласовать контролируемый повтор.
Не используйте новый заказ или повторную оплату как способ диагностики дубля.
Тестовое назначенное время к моменту повторной отправки может уже пройти.
Не повторяйте такой заказ без проверки времени и расписания.

Причина конкретного сбоя по скриншоту не установлена. Обновление не обещает
исправления настроек Saby и не выполняет повторную отправку существующих заказов.
Новых переменных и зависимостей нет. Сохраните data и текущие переменные.

## Начать с демонстрации

Архив содержит исходники. Это запускаемое приложение, а не просто макет.
По умолчанию никаких обращений к Saby и ЮKassa нет. Используйте вымышленные контакты.

1. Распакуйте архив и откройте терминал в папке с `main.py`.
2. Установите Python 3.12.
3. Выполните:

```sh
python -m venv .venv
# Linux/macOS:
. .venv/bin/activate
# Windows вместо предыдущей команды:
# .venv\Scripts\activate
pip install -r requirements.txt
python main.py
```

4. Откройте http://localhost:8000.
5. Добавьте товары → корзина → магазин/время/контакты → оформить.
6. Нажмите «Тестовая оплата · без списания».
7. Нажимайте кнопки симулятора продавца: сборка → готов → выдан.
8. Отправьте сообщение в чат: получите явно обозначенный демонстрационный ответ.

Демо-сессия изолирована cookie браузера. В другом браузере чужие заказы не видны.
Названия точек, адреса, товары и координаты — примеры, не реальные данные сети.
Встроенного предпросмотра без сервера нет: index.html нельзя открывать двойным щелчком.

## Что работает

- Адаптивная витрина, поиск, категории, корзина, выбор магазина, ближайшая точка по геолокации.
- Проверка цены и количества на сервере при создании заказа, выбор доступного времени.
- Сохранение заказов, сообщений, платежных идентификаторов в PostgreSQL; SQLite поддерживается для совместимости.
- Демо-платёж и симулятор статусов. Демо-кнопки недоступны в режиме integration.
- Проверка Telegram initData (HMAC, срок, защита от повторяющихся полей).
- Адаптер Saby: сервисная авторизация, каталог конкретного прайса с остатками,
  календарь, создание самовывоза, получение статуса.
- Адаптер ЮKassa: redirect-платёж, постоянный ключ идемпотентности, webhook с
  повторной проверкой через API, сверка суммы/валюты/заказа. Фоновая сверка каждые 15 сек.
- Текстовая поддержка: Mini App / личный бот ↔ Telegram-группа конкретного магазина.
  Ответ принимается только от Telegram ID продавца из staff_ids и только в группе его точки.
- Очередь Telegram-уведомлений сохраняется между перезапусками, до 8 попыток.
- Повторное подтверждение оплаты не создаёт повторный заказ.
- При неопределённом исходе POST в Saby повторная отправка блокируется до сверки.

## Честные границы версии

Локально проверен полный демонстрационный цикл и адаптеры на подставных ответах.
Реальные ключи Saby, ЮKassa, Telegram и доступ к Bothost не предоставлены:
никаких настоящих платежей, Saby-заказов и развёртывания не выполнялось.

Перед подключением нужно сверить ответы API вашего кабинета (обёртка каталога
`nomenclatures`, `externalId` созданного заказа, календарь и коды `productState`).
Адаптеры намеренно не подменяют ошибку внешнего API демонстрационными данными.
Если время самовывоза по вашему календарю требует дополнительного расчёта, этот
расчёт нужно настроить до пилота. Интервалы обрабатываются по опубликованной
документации Saby: 0 = 00:30, 47 = 00:00 следующих суток.

Поддерживаются фасованные товары в штуках/упаковках. Весовой товар с переменным
весом, модификаторы и маркировка не реализованы. Прайс должен содержать только
разрешённый для этого проекта безалкогольный ассортимент.

Чат позволяет согласовать замену, но автоматическое изменение оплаченного состава,
доплата, частичный возврат и фискализация возврата в 0.1 не реализованы. Такие случаи
оператор проводит вручную в ЮKassa и Saby, отдельно сообщает покупателю результат.
Отмена статуса Saby НЕ означает возврат денег: приложение не показывает её как возврат.
Фото/голосовые в поддержке и бонусные карты — следующий этап.

Остаток проверяется перед оформлением, но это НЕ резерв в Saby. За время оплаты
остаток может измениться. Для первой пилотной точки используйте фасованный ассортимент
со стабильным остатком; полноценный резерв и срок оплаты требуют следующей итерации.

В `delivery.paymentType` отправляется `card`, в комментарии указана внешняя оплата.
Это НЕ регистрирует повторный платёж. После выдачи продавец вручную выбирает ваш
неучитываемый тип оплаты в Saby Retail. Прототип НЕ вызывает `register-payment`.
Автоматическое отражение внешней оплаты отдельным типом не реализовано: проверить
на одном тестовом заказе вид карточки и завершение по вашей фактической процедуре.

## Bothost — сначала демо

1. Создайте отдельный проект/бот, загрузите эти файлы через поддерживаемый вашей панелью
   способ. При подключении GitHub поместите файлы в корень нового репозитория.
2. Используйте `Dockerfile` из архива или Python 3.12, `requirements.txt`, главный файл `main.py`.
3. В панели задайте порт 8000. Приложение слушает `0.0.0.0` и использует переменную `PORT`.
4. Подключите HTTPS-поддомен Bothost. Укажите его в `PUBLIC_URL`, без слеша в конце.
5. Переменные: `APP_MODE=demo`, `DB_PATH=/app/data/pickup.db`.
6. Проверьте постоянное хранение `/app/data` на вашем тарифе. Один контейнер, один процесс,
   без нескольких реплик/uvicorn workers. Перед обновлениями делайте резервную копию БД.
7. Запустите. `/health` должен вернуть `ok: true`. Откройте адрес и пройдите демо-цикл.
8. В BotFather создайте отдельного бота. Укажите HTTPS-адрес как Menu Button для Mini App.
   В демо не нужны секретные ключи. При необходимости проверить Telegram-вход задайте
   BOT_TOKEN; внешние уведомления в демо лучше не включать на рабочих группах.

В 0.4.0 PostgreSQL подключается через DATABASE_URL. Используйте один процесс: отдельная распределённая очередь для нескольких реплик пока не реализована.

## Подключить Saby и тестовую ЮKassa

1. Настройте «Доставку», самовывоз и прайс в Saby. Убедитесь в наличии API-доступа.
2. Добавьте приложение Saby с сервисной авторизацией. Секреты сохраняйте только в переменных
   Bothost, не в GitHub и не в переписке. См. `.env.example`.
3. В 0.4.0 используйте SABY_STORE_PRICES, SABY_STORE_CHATS и SABY_STORE_STAFF из START_HERE.md. Для справки, поля старого `config/stores.json`:
   - `id`: внутреннее короткое имя, например `belinskogo`;
   - `name`, `address`, `lat`, `lon`: отображение магазина;
   - `point_id`: ID точки продаж Saby;
   - `price_list_id`: ID опубликованного прайса для этой точки;
   - `chat_id`: ID служебной Telegram-группы;
   - `staff_ids`: разрешённые Telegram ID продавцов.
4. Укажите `SABY_CLIENT_ID`, `SABY_APP_SECRET`, `SABY_SECRET_KEY`.
5. Укажите `YOOKASSA_SHOP_ID` и тестовый `YOOKASSA_SECRET_KEY` (начинается с `test_`).
   Сохраните `ALLOW_REAL_PAYMENTS=false`. Тестовый платёж денег не списывает.
6. Укажите `BOT_TOKEN`, `BOT_USERNAME` без @, случайный `TELEGRAM_WEBHOOK_SECRET`
   длиной от 24 символов, `ADMIN_CHAT_ID` для уведомлений об ошибках передачи.
7. Установите `APP_MODE=integration`, `PUBLIC_URL=https://ВАШ-ДОМЕН`, запустите.
   ВНИМАНИЕ: тестовая оплата в integration создаёт НАСТОЯЩИЙ заказ в подключённом Saby.
   Используйте согласованную тестовую точку и предупредите продавца; заказ не является продажей
   до ваших действий в Saby. Изолируйте пилот от покупателей.
8. В терминале контейнера выполните `python manage.py telegram-setup`.
   Команда устанавливает webhook и кнопку меню бота. Добавьте бота в группы магазинов.
   Продавцы отвечают именно Reply на сообщения бота. Покупатель предварительно нажимает /start.
9. В ЮKassa настройте URL уведомлений `https://ВАШ-ДОМЕН/webhooks/yookassa`, события
   `payment.succeeded` и `payment.canceled`. Пропущенное уведомление восстановит опрос API.
10. Оформите тестовый заказ. Проверьте магазин, ассортимент, цену, время и комментарий.
11. На каждом этапе в Saby получите статус:
    `python manage.py saby-state UUID_ЗАКАЗА_SABY`.
    Заполните `SABY_STATE_MAP` соответствием наблюдаемых `productState` значениям
    `accepted`, `collecting`, `ready`, `completed`, `canceled`. Коды нельзя угадывать.
    Например структура переменной: `{"КОД_ИЗ_SABY":"ready"}` — замените на реальные коды.
12. Закройте тестовый заказ вашим неучитываемым типом оплаты. Убедитесь, что приложение
    показывает «Выдан», движение товаров верно, повторный чек не сформирован.

## Электронные чеки и реальные платежи

В 0.1 реальные платежи по умолчанию заблокированы. Техническая возможность
включить их не означает готовность процесса фискализации к эксплуатации.

Адаптер может передать чек 100% предоплаты (`full_prepayment`) при создании платежа:
`RECEIPT_ENABLED=true`, верный `RECEIPT_VAT_CODE` и, если нужен, `RECEIPT_TAX_SYSTEM`.
Налоговые значения не угадываются. Требуются подключённые услуги фискализации в ЮKassa.
Чек окончательного расчёта при выдаче и чеки возвратов прототип автоматически не создаёт.
До реальных платежей нужно настроить их во внешнем сервисе/ручном процессе и проверить
вместе с вашим закрытием неучитываемым способом. Для смешанных ставок НДС потребуется
ставка на каждой позиции — единая ставка прототипа для такого прайса не подходит.

Условие пилота: проверены чеки, возврат, отражение в Saby, статусы, политика обработки
персональных данных и реквизиты ИП в интерфейсе (заменить демонстрационный текст),
настроены резервные копии, наблюдение за ошибками и ответственное лицо.
Только после этого `LIVE_ACCEPTANCE_CONFIRMED=true` + `ALLOW_REAL_PAYMENTS=true` и боевой ключ.

## Если заказ оплачен, но передача в Saby под вопросом

Saby order/create в прочитанной документации не гарантирует клиентский ключ
идемпотентности. Поэтому слепые повторы опасны.

- UI показывает «Оплачен · уточняем передачу магазину», денег повторно не просит.
- Уведомление уходит в ADMIN_CHAT_ID, локальный заказ остаётся в БД.
- `python manage.py attention` — список таких заказов.
- Найдите заказ в Saby по полному ID в комментарии.
- Остановите приложение. Если найден: `python manage.py attach-saby ЛОКАЛЬНЫЙ_ID SABY_UUID`.
- Только если убедились, что заказа в Saby нет:
  `python manage.py retry-saby ЛОКАЛЬНЫЙ_ID --confirmed-absent`.
- Запустите приложение. При attach проверьте правильность магазина, покупателя и суммы вручную.

Интервал опроса и очереди — 15 секунд. Не используйте несколько процессов с общей SQLite.
Telegram может доставить повторное уведомление после аварии между отправкой и записью
результата; на количество платежей и заказов это не влияет.
